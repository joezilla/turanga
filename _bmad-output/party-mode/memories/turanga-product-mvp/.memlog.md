- (event) Context inherited: turanga = agentic platform (Dify/Hermes-like). Users: agent builders+operators now (owner only), business owners later. Internal-tool stakes. Warm Ink design baseline. UX spines exist for Login, Agent-definition (Dify-style full: model+prompt+tools+knowledge+variables+test pane), Settings (providers/profile/workspace/billing).
- (decision) THE ITCH (fork decided): security/isolation is the wedge. User likes Hermes/Openclaw but distrusts their lack of sandboxing. Core want: truly sandbox agents so they can be given real access safely (e.g. an email-analysis agent immune to prompt-injection despite broad access). Plus hard cost control/limits per agent or agent-group.
- (decision) VISION: a centrally-managed personal ecosystem of agents + apps/databases. Concrete use cases: manage stock portfolio, manage email, manage home automation. Prosumer/personal-first, not enterprise-first.
- (event) FEATURE DUMP (roadmap, not MVP): Lifecycle=create/manage/secure/run. Agent: draft(scratchpad)->test->promote(Activate); cost control; model routing; security(sandbox run, PII detection, prompt-injection defense, custom pre-activation checks); run custom code/libs; skills/MCPs w/ permission scoping; self-learning/skill-update (optionally human-gated); memory mgmt. Skills: central mgmt, scratchpad/activate, env-specific macro language executed at runtime. MCP: central tool mgmt. Connections: manage connections+models, local inference (llama.cpp), OpenRouter. Workflows: agents sit in workflows; eventing kicks off workflows/agents.
- (event) Competitors named: dify, openclaw, hermes. [Mary flag: verify Openclaw/Hermes specifics before asserting — niche/fast-moving.]
- (decision) WEDGE CONFIRMED: security leads ('agents you can trust with access'), cost control rides shotgun, ecosystem is the promise.
- (decision) CRITICAL CORRECTION: turanga is a GENERIC horizontal platform, NOT a use-case product. It must NOT hardcode email/portfolio/home. Those are things the user builds ON turanga. MVP proves generic primitives; email is a dogfood proof case, not a baked-in feature. (Overrides earlier 'inbox agent is the MVP' vertical framing.)
- (decision) SANDBOX definition (v1): OS-level containers per agent PLUS a wrapper around the agent harness that guards data ingress/egress (controls what data goes in and what can leave). This is the core security primitive.
- (decision) MVP cost cap: start simple — per-agent, time-window budget (e.g. $X/day, kill on breach). Per-run/per-group deferred.
- (decision) MVP in/egress guard: rules/allowlist only (connection may only reach allowed destinations), BUT built as a pluggable FILTER mechanism so content-inspection/PII-scan can be added later without rework.
- (decision) MVP scope = single-user / solo, single-machine. Multi-user/roles deferred (different security model).
- (decision) PRODUCT DEFINITION (locked): turanga is a generic platform for building, securing, and operating your own ecosystem of agents. Every agent runs in a sandbox you control (container + guarded data in/egress) under a hard cost ceiling, moved deliberately draft->test->Activate. Nothing in the platform knows what an agent does. Wedge: agents you can trust with real access (security leads, cost rides shotgun, ecosystem is the promise). Competitors: Dify/Openclaw/Hermes (capable but not isolation-first).
- (decision) MVP DEFINITION (locked): irreducible generic core = (1) define agent [model+instructions+skills+scoped permissions]; (2) lifecycle draft->test->Activate; (3) sandboxed run [container + in/egress guard w/ pluggable filter]; (4) hard cost cap per-agent time-window w/ live meter + kill; (5) one generic connector + central mgmt of agents/connections/keys; (6) dogfood proof: an email agent built ON the platform, Activatable against a real inbox, with ZERO email-specific platform code. Solo/single-user. Roadmap (OUT): workflows+eventing, self-learning, runtime macro language, MCP marketplace, model routing, local llama.cpp, multi-agent, full PII engine, multi-user/roles.
