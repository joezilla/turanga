# Deferred Work

## Deferred from: code review of Epic 12 (12.1–12.3) — 2026-08-06

### MUST address in Story 12.4 (the harness AI SDK loop — `toolLoop.ts` is not yet wired into `main.ts`, so these are latent until 12.4 ships)

- **[HIGH] Duplicate op-name cross-tool collision → wrong tool/credential invoked.** `toolLoop.ts` `buildTools` keys the SDK ToolSet by op **name only** (`tools[name] = tool({...})`), ignoring `t.id`. If two attached tools each grant an op named `search`, the second overwrites the first — a model call to `search` is silently brokered against the wrong tool's `toolId` + credential + endpoint. A cross-tool misroute with no error. Fix: namespace the SDK tool key by `toolId` (and map back to the real op on invoke), or reject/disambiguate colliding names at resolve time.
- **[HIGH] Mid-loop kill/gateway error throws out of `generateText`; no partial text salvaged.** `runToolLoop` has no try/catch around `generateText`. A cost-cap breach or gateway error → `makeGuardFetch` returns HTTP 502 → the SDK throws → `runToolLoop` rejects with zero final text. This contradicts the epic AC ("killed run ends cleanly, last text stands") and the `toolLoop.ts` comment. Fix: wrap `generateText`, map the thrown gateway/kill error to a `stopReason` (`cost-cap-kill` / `error`) + best-effort accumulated text, and correct the comment. (Ties to Story 12.5/12.6 stop-reason + observability.)
- **[MED] Guard returns provider `tool_calls` unvalidated; a non-string `arguments` makes the harness reject the ENTIRE response.** `guard.ts` casts `choice.message.tool_calls as GuardModelToolCall[]` with no re-validation; the harness then does a strict `GuardModelResponseSchema.parse` (requires `function.arguments: z.string()`). LiteLLM normally normalizes `arguments` to a JSON string, but any provider/mode surfacing it as a parsed object → strict parse fails → `guardModelCall` returns "unreadable response" → the loop dies though the model produced valid calls. Fix: validate/coerce `tool_calls` against `GuardModelToolCallSchema` at the Guard (JSON.stringify an object `arguments`) before returning. (Guard-side fix, but only bites once the loop drives it → 12.4.)
- **[LOW] `inputSchema` fail-safe checks object-ness, not JSON-Schema validity.** A registered op whose `inputSchema` is a valid object but a non-object-typed schema (`{type:"array"}`, `{type:"string"}`, a `$ref`) passes the 12.2 `isSchemaObject` gate and is forwarded to LiteLLM, which requires function `parameters` to be a `type:"object"` schema → the model call 400s the whole run. Heavily mitigated: the MCP SDK validates `inputSchema` as an object at registration, so this is a defense-in-depth gap, not a normal-path bug. Fix (12.4 hardening): validate the schema shape before passing to `jsonSchema()`, or fall back to a permissive object schema on a non-object-typed registration.
- **[LOW] Tool executor conflates a permission refusal and a tool error into one `{error}` shape.** `toolLoop.ts` returns `{error: refusal?.detail ?? error ?? ...}` for both a Guard permission refusal and an MCP tool error. The model can't distinguish "not allowed" from "the tool failed" → it may retry a permanently-denied op repeatedly, burning steps against the cap. Fix: surface the refusal kind distinctly so the model stops retrying a denied op.
- **[LOW] `makeGuardFetch` couples to SDK message-`content` shape.** `GuardModelMessageSchema.content` is `string | null`. If the AI SDK ever serializes `content` as an array of parts (multimodal / certain tool-result encodings), the Guard's `safeParse` fails → 400 → the loop ends with a misleading error. LOW today (the openai-compatible provider emits strings for the text/tool path). Fix: normalize in `makeGuardFetch` or widen + normalize Guard-side.
- **[note] Empty `tools: []` (vs undefined) forwards `tool_choice:"auto"` with zero tools.** Both `guard.ts` and `toolLoop.ts` gate on truthiness (`req.tools ?`), and `[]` is truthy. A caller sending an empty tools array would forward `tool_choice:"auto"` with no tools → some gateways 400. No caller does this today (the shipped stub sends no tools). Being patched guard-side now; apply the same `?.length` gate in `toolLoop.ts` when it lands in 12.4.

### Deferred — pre-existing / by-design (not caused by Epic 12)

- **[pre-existing] A 200 response with a malformed/empty body is returned as `ok:true, text:""`.** `proxyModel` does `r.json().catch(()=>({}))` and `content ?? ""` — a gateway fault (non-JSON 200, `choices:[]`, `content:null`) is masked as a blank successful answer. Pre-dates Epic 12; in a loop it would terminate silently. Consider surfacing an error for an empty/undecodable 200.
- **[by-design] A stale v8 harness image hard-fails every v9 spec.** The `CONTRACT_VERSION` literal mismatch fails `JobSpecSchema.parse` for all specs until the harness image is rebuilt in lockstep. This is the intended version-pin contract (Story 12.1 documents the required image rebuild); flagged for deploy awareness (no rolling-deploy grace).
- **[by-design] `RunMessage` / `ControlChannelMessageSchema` are v9-only.** Stored pre-bump (`v:8`) transcripts would be rejected by any server-side re-validation against the v9 schema. This is the recurring, accepted cost of every contract bump (2→…→9); specs/messages are version-pinned by design.

## Deferred from: code review of Epic 12 (12.4–12.7) — 2026-08-07

Six patches were applied at review time (SDK↔Guard wire-compat test; Guard normalizes provider tool_calls' `arguments` to a string + drops malformed; a final uniqueness guarantee in `buildTools`; the capability signal now requires a selected model + ≥1 grant; a refusal-path test; empty-string `done.reason` treated as absent). The below were triaged as real-but-deferred.

- **[LOW/bounded] Parallel malformed tool calls in one step → N metered `generateObject` repairs.** `stepCountIs(N)` bounds STEPS, not repairs-per-step, and repair round-trips aren't counted as steps. Bounded by the per-run cost cap (each repair is a metered Guard call, kill-on-breach applies), so no unbounded-spend hole — but a per-step repair cap would be tighter. Weak models emit ~1 call/step in practice.
- **[LOW] Cost-cap-kill late-settle mislabel.** If the Guard's out-of-band `kill` callback arrives >250ms after the harness `done` (rare — the kill is emitted synchronously in the same `proxyModel` call), the run is recorded `failed` + the new `done.reason` ("ended before a final answer") instead of `killed` + the cost-cap reason. 12.6 makes the (pre-existing) mislabel more confidently worded. Consider widening the settle or having the harness not assert a reason on a bare model failure.
- **[LOW] Transcript "Ended —" line vs status dot can disagree after a kill/timeout override.** The harness `done{reason:"…before a final answer"}` is persisted + SSE-relayed before the orchestrator overrides the terminal to `killed`; `RunTranscript` renders the stale `done.reason` while the status dot shows the kill. Fix: pass the run's terminal status to `RunTranscript` and suppress the "Ended —" line on `killed`/timeout (or reconcile the two reason surfaces).
- **[LOW] Step-limit truncation invisible outside the transcript.** A step-limit run is `succeeded` + reason; `runCause` is status-gated (quiet on succeeded), so a compact run list (not the full transcript `done` row) shows it as a clean success. The "never a silent clean finish" guarantee holds only in the transcript. Consider surfacing `run.reason` on succeeded runs in list views.
- **[LOW] Non-`stop` finishReason at the ceiling is labeled "step-limit".** `hitCeiling = steps>=MAX && finishReason!=="stop"` — a token-length cutoff (`finishReason:"length"`) on step 10 reads "Reached the step limit". Minor mislabel.
- **[LOW] `isToolVerified` substring match → coincidental false-negative.** A local model id containing a verified substring (e.g. `my-gpt-4o-clone`) is treated as verified → no signal. Advisory-only (a missing warning, not a broken run). Harden with a token-boundary match on the post-prefix segment if it matters.
- **[LOW] `MAX_STEPS` is a hardcoded const, not "configurable".** Story 12.4 AC1 says "configurable, default ~10"; the control backstop exists but isn't tunable (no env/spec override). Add a spec field or env override if per-agent tuning is wanted.
- **[disclosed — not a defect] Skills-read context is not folded into the tool loop.** A skills+tools agent's Phase-1 read-op notes reach the model on the no-tools path but not inside `runToolLoop` (which builds context from `toPrompt(spec)`). This is an OPEN QUESTION explicitly documented in the 12.4 story (agents are skills-XOR-tools in practice) — deferred by design, not a hidden regression.
